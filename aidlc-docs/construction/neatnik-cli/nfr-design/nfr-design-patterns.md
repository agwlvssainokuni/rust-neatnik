# NFR Design Patterns: neatnik-cli

## 1. Resilience Patterns

### リトライなし・フェイルファスト(Q D1=A)
- ファイルI/O操作でエラーが発生した場合、リトライは行わない。当該ファイルを`StageOutcome(Failed)`として記録し、次の候補ファイルの処理を継続する(business-logic-model.md 5章)
- 「次回実行時の再対象化」(BR-7)が実質的なリトライの役割を果たす。cronによる定期実行という実行方式(NFR-4)と自然に噛み合う設計

### グローバルエラーハンドラ(SECURITY-15)
- `main.rs`のエントリポイントで、パイプライン全体を`anyhow::Result`で受け、失敗時は:
  - ユーザー向けには一般化されたエラーメッセージ(内部パス・スタックトレースを含まない)を標準エラー出力に表示
  - 詳細はtracing経由で構造化ログに記録
  - 適切な終了コード(0=成功、非0=失敗の種別に応じたコード)を返す
- ジョブロック・一時ファイルハンドル等のリソースは、Rustの所有権システム(Drop)を活用して、エラーパスでも確実に解放する

## 2. Scalability Patterns
**該当なし**。単一ユーザー・単一ホストで動作するローカルCLIバッチツールであり、水平スケーリングやスループット拡張の概念が存在しない(execution-plan.md リスク評価、NFR Design Plan参照)。

## 3. Performance Patterns

### ストリーミングスキャン
- `walkdir`のイテレータを直接消費し、対象ファイル一覧を一度にメモリ上へ全件収集しない
- 候補ファイルは発見次第、逐次パイプライン処理(business-logic-model.md 3章)に渡す。ただしバンドル圧縮(4章)は期間キーごとのグルーピングが必要なため、その期間キーの単位でのみ候補を保持する(全件ではない)

## 4. Security Patterns

### 脅威モデル(Q D2=B)
設定ファイル(YAML)は、共有環境等での改ざんや設定ミスにより`半信頼`とみなす。特に、削除・移動という不可逆/破壊的操作を行うツールであるため、設定内容に起因する意図しないディレクトリへの影響を防ぐ設計とする。

### パストラバーサル対策
- 各`WatchTarget.basedir`は起動時に正規化(canonicalize)する
- `include`/`exclude`パターンでマッチした各候補ファイルの正規化後の絶対パスが、正規化済み`basedir`の配下に収まっていることを検証する。収まっていない場合(`..`を含むパターンや、symlink経由での脱出等)は、そのファイルを対象から除外し警告ログに記録する
- `RelocateConfig.destination`は固定の絶対パスであり、`include`/`exclude`のような可変パターンに由来しないため、同種のトラバーサルリスクは相対的に低いが、正規化と存在確認は行う

### サプライチェーン(SECURITY-10)
- `cargo-deny`の設定(`deny.toml`)で、脆弱性アドバイザリ・非承認ライセンス・重複依存を検査する(tech-stack-decisions.md)
- 既知の問題があるクレート(`serde_yaml`, `serde_yml`)は明示的に使用しない

### ロギング(SECURITY-03)
- `tracing`のグローバルサブスクライバを`main.rs`で一度だけ初期化し、`tracing-subscriber`のJSONフォーマッタで構造化出力する
- ログにシークレット・認証情報は含まれない(そもそも本ツールは認証情報を扱わない)
